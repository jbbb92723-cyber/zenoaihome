# ZenoAIHome 网站前后台一体化优化架构方案 v2.0

> 日期：2026-08-13
> 状态：实施基线
> 适用范围：`Zeno-Code/zeno-site/` 的前台、用户系统、管理后台、业务 API、支付、AI 与内容管道
> 配套基线：[网站后台重构与 API 治理技术方案-v1](./网站后台重构与API治理技术方案-v1.md)

---

## 0. 先给结论

当前网站不需要换技术栈，也不需要再增加一套后台。

推荐路线是：

> **保留 Next.js + Auth.js + Prisma + Supabase + Vercel 的模块化单体，先修可信主链，再收敛前台入口，最后把后台变成一人公司的行动台。**

当前最大的风险不是页面不够多，而是页面给人的承诺已经超过后端实际兑现能力：

- 付款入口尚未达到可交易状态；
- 数据库异常可能被伪装成空数据或成功；
- 订单、支付、权益之间的状态没有统一闭环；
- 前台存在旧产品和当前产品的价格、承诺冲突；
- 后台展示了大量资产数量，却没有优先告诉经营者今天该做什么；
- 用户提交微信、邮箱、电话、居住偏好和项目资料后，看不到清晰的数据使用边界。

因此，接下来 30 天的目标不是“继续做大网站”，而是完成一条可验证、可追踪、可复盘的主链：

```text
用户进入
  -> 找到自己当前的问题
  -> 使用一个工具或阅读一份证据
  -> 得到明确的判断与下一步
  -> 提交服务申请
  -> 人工确认范围与交付物
  -> 付款
  -> 权益或项目交付
  -> 用户验收
  -> 结果沉淀为案例、内容和角色知识
```

这条链跑通后，网站才真正成为 IP 的信任中枢，而不是功能集合。

## 1. 架构目标与非目标

### 1.1 业务目标

网站承担四个职责：

| 层 | 网站要解决的问题 | 主要产物 |
| --- | --- | --- |
| 认知层 | 用户为什么相信赞诺 | 经历、判断、边界、证据 |
| 自助层 | 用户现在能不能先自己解决 | 工具、清单、风险词典、公开文章 |
| 承接层 | 用户拿不准时如何继续 | 服务申请、报价、协议、支付 |
| 复利层 | 每次实践如何让 IP 变强 | 交付结果、案例、方法卡、角色知识 |

### 1.2 技术目标

1. 任何关键写操作都能明确回答：谁做的、写入了什么、是否成功、失败在哪里。
2. 任何订单都能从创建、付款、权益发放到完成被完整追踪。
3. 前台、后台、API 和内容资产使用同一套业务词汇和状态定义。
4. 公开内容、用户数据、管理员数据和内部自动化有清晰的权限边界。
5. 在当前单人团队规模下保持低运维成本，不提前引入微服务和独立 API 网关。

### 1.3 明确不做

- 不整体 fork 通用 SaaS 后台。
- 不把网站改造成装修知识百科或 AI 工具目录。
- 不同时维护多套价格阶梯和产品承诺。
- 不新增没有真实用户、交付物和验收标准的页面。
- 不拆微服务、Kubernetes、消息总线或独立 API Gateway。
- 不以 `prisma db push` 作为生产数据库变更方式。
- 不让 AI 自动替代报价、合同、支付和交付决策。

## 2. 当前系统基线

当前代码已经具备较完整的模块化单体骨架：

- 约 103 个页面路由、39 个 API 路由；
- Next.js 14 App Router；
- Auth.js v5 + Credentials/Google；
- Prisma + PostgreSQL/Supabase；
- 用户、会员、服务申请、订单、优惠券、兑换码；
- 商机、方案、协议、项目、交付物；
- AI 聊天、AI 回复、内容草稿与 Hermes 管道；
- 自定义 Zeno OS 管理后台。

这说明基础设施已经超过“个人博客”阶段，但也产生了架构债务：业务域、历史页面和未来规划同时存在，导致系统的表面成熟度高于真实业务验证程度。

### 2.1 现有方案继续沿用的部分

现有 [v1 技术方案](./网站后台重构与API治理技术方案-v1.md) 中以下决策继续有效：

- 保留 Next.js + Auth.js + Prisma + Supabase + Vercel；
- 采用模块化单体；
- 统一 Route Handler / Server Action 的鉴权、校验、限流、审计；
- 生产数据库使用 migrations；
- AI、邮件、飞书、微信和图片服务使用 Provider Adapter；
- 先完成核心业务闭环，再考虑通用后台或独立服务。

### 2.2 本方案新增的重点

v1 主要解决后台和 API 治理；v2 增加三个业务架构约束：

1. **前台按用户当前场景组织，而不是按你的能力清单组织。**
2. **后台按今日行动和承诺履约组织，而不是按资产数量组织。**
3. **每次交付必须有“结果 -> 案例 -> 角色知识”的回流接口。**

## 3. 目标业务架构：角色知识体系驱动的 IP 主站

你的核心产品不是“AI 培训、知识库、智能体、网站开发”五个并列能力，而是：

> **帮助传统行业实践者，把经验升级为可验证、可调用、可传播、可交付的角色知识体系。**

网站中的业务对象应按下面的关系理解：

```text
赞诺（IP 主体）
  |
  +-- 角色知识体系：核心方法和判断边界
  |
  +-- 装修视野：最深的垂直验证场
  |
  +-- OPC：一人公司经营方式
  |
  +-- 星火者：实践、反馈与协作网络
  |
  +-- 网站：证据、工具、服务和结果的公开中枢
```

### 3.1 三类核心角色

“角色知识体系”不是给所有人展示的资料分类，而是把同一条经验按使用者的责任、场景和输出重组。

| 角色 | 典型问题 | 需要的知识形态 | 网站入口 |
| --- | --- | --- | --- |
| 决策者/业主 | 我现在该判断什么，如何降低错误成本 | 风险规则、检查清单、案例、下一步 | `/tools`、`/living-diagnosis` |
| 实践者/同行 | 我如何把经验变成稳定交付 | 方法卡、SOP、角色边界、复盘 | `/blog`、`/knowledge` |
| OPC/创业者 | 我如何把个人能力变成可持续业务 | 产品、获客、交付、协作、资产化 | `/ai-tools`、`/community` |

同一条内容可以服务多个角色，但前台展示时必须标明“这条内容帮谁做什么决定”。

### 3.2 内容到商业的回流

每个重要内容单元至少带有以下元数据：

```text
角色：谁使用
场景：什么时候使用
问题：要避免什么错误
判断：赞诺如何判断
动作：用户下一步做什么
证据：来自哪次实践或材料
交付：能形成什么工具、服务或结果
```

没有场景、判断和动作的内容，只是知识展示，不进入核心转化链。

## 4. 前端优化方案

### 4.1 前台的第一原则：先解决用户当前问题

首页不能要求用户先理解完整品牌架构。首屏应该同时回答三件事：

1. 你是谁；
2. 你现在具体解决哪类问题；
3. 用户今天可以先做哪一个动作。

建议首屏固定为：

```text
从传统行业走进 AI 的实践者
我把真实经验整理成判断、工具和可交付的方法。

[我正在装修] [我在做一人公司] [我想把经验系统化]
```

三个入口不是装饰性标签，点击后要进入三条独立路径，页面上的主要 CTA、案例和相关内容随角色改变。

### 4.2 主导航收敛

主导航建议保持 6 项以内：

```text
首页 | 公开实践 | 免费工具 | 项目合作 | 星火者 | 关于
```

处理原则：

- `blog`、`notes`、`knowledge`、`cases`、`resources` 不全部作为一级导航；归入“公开实践”。
- `tools` 与 `ai-tools` 不让用户猜区别；前台统一称为“免费工具”，内部可保留不同路由。
- `opc-knowledge` 只保留为方法档案或重定向目标，不作为独立销售页。
- `/start`、旧装修路线、重复服务页保留 SEO 和历史访问，但明确 canonical、重定向或降级为辅助内容。
- 不在同一层同时出现“装修产品价格”“OPC 课程价格”“星火者价格”，除非它们来自同一份产品真源。

### 4.3 三条用户路径

#### 路径 A：装修决策者

```text
内容/搜索
  -> 报价初筛或居住诊断
  -> 输出风险点、追问清单、下一步
  -> 用户选择自助、人工快审或深度合作
  -> 交付与验收
  -> 脱敏案例回流
```

前端要求：

- 工具结果必须明确“这不是法律意见/不是最低价承诺/不是替你签约”；
- 结果页只给一个主 CTA，最多两个辅助动作；
- 每个服务页展示输入材料、交付物、周期、验收方式和不适合人群；
- 用户提交材料前说明保存位置、用途和人工查看范围。

#### 路径 B：传统行业实践者

```text
文章/短视频
  -> 一个具体判断样张
  -> 方法卡或模板
  -> 申请一次小范围交流/服务
  -> 形成自己的角色知识
```

前端要求：

- 先展示真实过程，不先展示抽象“AI 赋能”；
- 每篇文章末尾给出“可拿走的动作”和“适用边界”；
- 用案例说明输入和输出，不用功能名替代价值。

#### 路径 C：OPC 创业者

```text
一人公司诊断
  -> 找到当前卡点：定位/获客/交付/复利
  -> 读取对应公开实践
  -> 使用一个方法卡或任务规划器
  -> 加入星火者或提交具体合作问题
```

前端要求：

- OPC 页面不得承诺收入、客户、项目或合伙资格；
- 星火者是关系和实践产品，不包装成课程或发财方案；
- 诊断结果要告诉用户“现在不适合做什么”，减少选择负担。

### 4.4 页面模板统一

重要页面采用同一信息结构，减少用户重新学习：

```text
1. 这是谁的什么问题
2. 先得到什么结果
3. 输入什么材料
4. 系统/赞诺如何判断
5. 输出什么
6. 不解决什么
7. 下一步只有一个主动作
8. 证据、案例或样张
```

禁止用以下内容替代证据：

- “全链路”“赋能”“闭环”“系统化”等抽象词；
- 无来源的成功数字；
- 尚未运行的价格阶梯；
- 只有截图、没有输入输出说明的样张。

### 4.5 前端技术改进

1. 把首页、服务页和工具页中的重复 CTA、状态标签和边界声明抽成共享组件。
2. 统一使用服务端产品真源生成产品名、价格、权益和退款规则。
3. 对动态用户页面先检查 session，再访问数据库；禁止 `session!` 强制解引用。
4. 付款页在收款配置缺失时明确显示“暂不可付款”，不要渲染看似可用的空二维码。
5. 用 `next/image` 替换后台和关键页面的原生 `<img>`。
6. 将中文字体本地化，减少构建对 Google Fonts 网络的依赖。
7. 保留 `eslint` 和 TypeScript 门禁；逐步恢复生产构建中的 lint，不长期依赖 `ignoreDuringBuilds`。
8. 首屏只加载必要交互，后台图表和低频模块继续动态加载。

## 5. 后台优化方案：从资产大屏到行动台

### 5.1 后台第一屏只回答五个问题

登录后不应先看“网站有多少页面”，而应先看：

1. 今天有谁等待回复？
2. 哪些申请或订单超过承诺时间？
3. 哪些付款需要确认或权益尚未发放？
4. 哪些项目或交付物等待验收？
5. 哪些结果可以沉淀为案例和角色知识？

建议大屏第一行改为：

```text
今日待办 | 超时承诺 | 待确认付款 | 待验收交付 | 待回流知识
```

资产统计（文章数、内容单元、Git 提交）降为“系统健康”二级区域。

### 5.2 后台模块职责

| 模块 | 核心任务 | 主要对象 | 首要指标 |
| --- | --- | --- | --- |
| 今日行动 | 排序和执行待办 | Activity、SLA、任务 | 逾期数、今日完成数 |
| 线索与服务 | 处理用户问题 | ServiceRequest、Opportunity | 首次响应时间、转化率 |
| 订单与权益 | 确认钱和兑现承诺 | Order、Payment、Entitlement | 待确认时长、重复发放数 |
| 项目交付 | 让结果可验收 | Project、Deliverable | 按期交付率、待验收数 |
| 内容回流 | 把结果变成资产 | Draft、Case、Knowledge | 回流完成数、复用次数 |
| 系统健康 | 发现故障和配置问题 | Readiness、Error、Usage | 错误率、外部服务可用性 |

### 5.3 后台核心工作流

#### 服务申请到交付

```text
submitted
 -> reviewing
 -> scoped
 -> proposed
 -> accepted
 -> delivering
 -> awaiting_acceptance
 -> completed
```

`rejected`、`cancelled`、`returned` 是终止或回退状态，不能用“completed”代替所有人工处理结果。

每次状态变更必须记录：

```text
actorId / actorRole / before / after / note / requestId / createdAt
```

#### 订单到权益

不要用一个 `Order.status` 同时表示订单、支付和交付。建议拆为：

```text
Order.status:      pending | confirmed | fulfilled | cancelled | refunded
Payment.status:    pending | succeeded | failed | refunded
Entitlement.status: pending | active | expired | revoked
```

业务链：

```text
创建订单
 -> 创建支付记录
 -> 验签支付事件
 -> 幂等确认 Payment
 -> 事务发放 Entitlement
 -> 写入审计和用户通知
```

任何一步失败都必须可重试，不能给用户显示“已成功”却没有数据库事实。

#### 结果到知识

```text
交付完成
 -> 用户验收
 -> 脱敏与授权
 -> 案例草稿
 -> 角色知识单元
 -> 网站/公众号/短视频装配
```

“保存到知识库”必须是真实创建知识记录，并关联来源项目、服务申请、案例和授权状态。

### 5.4 权限模型

| 角色 | 可读 | 可写 | 禁止 |
| --- | --- | --- | --- |
| USER | 个人账户、自己的申请/订单/权益 | 自己的资料和申请 | 任何后台数据 |
| OPERATOR | 内容、服务、项目（脱敏必要数据） | 服务状态、交付状态、草稿 | 支付配置、权限、密钥、删除 |
| ADMIN | 全部 | 全部高风险操作 | 无，但高风险动作需二次确认 |

后台 layout 不是安全边界。每个 Server Action 和 Route Handler 都必须独立调用权限函数。

建议从 `isAdminUser()` 升级为：

```ts
requirePermission(actor, 'orders:confirm')
requirePermission(actor, 'projects:write')
requirePermission(actor, 'knowledge:publish')
```

## 6. 后端优化方案

### 6.1 先移除“静默容错”

当前 `lib/prisma.ts` 的 fallback 适合构建期避免数据库访问，不适合生产业务写入。

目标规则：

- 生产环境没有 `DATABASE_URL`：启动或 readiness 失败；
- 数据库查询失败：返回标准 `SERVICE_UNAVAILABLE`，并记录 requestId；
- 写入失败：绝不返回 `ok: true`；
- 公开诊断可以在明确标记 `persisted: false` 时返回本地计算结果；
- 订单、服务申请、注册、权益和后台写入失败必须让用户知道没有完成。

建议拆成两种客户端：

```text
prisma        -> 真实客户端，失败抛错
tryRead       -> 只有低风险公开读页面可以使用
```

不要用 Proxy 全局吞掉异常。

### 6.2 统一 API 分层

建议目录逐步演进为：

```text
lib/
  api/
    errors.ts
    response.ts
    guard.ts
    request-id.ts
  auth/
    session.ts
    permissions.ts
  domains/
    services/
    commerce/
    projects/
    knowledge/
    content/
  integrations/
    ai/
    payment/
    email/
    wechat/
```

Route Handler 只做：认证、输入校验、调用领域服务、响应映射。状态机和事务不能散落在页面组件或 API 路由中。

### 6.3 标准错误响应

成功：

```json
{
  "ok": true,
  "data": {},
  "requestId": "req_xxx"
}
```

失败：

```json
{
  "ok": false,
  "error": {
    "code": "DATABASE_UNAVAILABLE",
    "message": "系统暂时无法保存，请稍后重试。"
  },
  "requestId": "req_xxx"
}
```

生产响应不能暴露 SQL、堆栈、环境变量名或第三方完整响应。

### 6.4 订单与支付

当前优先采用“人工转账 + 后台确认”的稳定 MVP，暂不同时接入多个自动支付渠道。

人工支付必须具备：

1. 两张真实收款码和收款主体说明；
2. 订单号、金额、退款规则和确认时限；
3. 用户点击“已付款”后进入 `pending_confirmation`；
4. 后台确认使用条件更新，防重复确认；
5. `grantEntitlement()` 幂等；
6. 权益发放失败时订单不显示完成；
7. 操作日志带操作者、前后状态和备注。

如果接入自动支付，再新增支付 Provider Adapter：

```text
raw body
 -> provider signature verify
 -> eventId unique check
 -> payment record update
 -> order state transition
 -> entitlement transaction
 -> notification
```

占位 Webhook 在未实现前应返回 `503` 或明确 `501`，不能对任意事件返回业务成功。

### 6.5 优惠券与兑换码

- 创建订单时真正校验 `couponCode`；
- 折扣计算、使用次数占用、订单创建放在同一事务；
- 兑换码使用次数用条件更新，防并发超发；
- 所有权益发放以唯一约束和幂等键保护；
- 每一笔优惠和权益都记录来源订单。

### 6.6 AI 与第三方调用

所有 AI、邮件、飞书、md2wechat、微信和图片调用统一具备：

- 服务端密钥；
- 超时、最大输入和最大输出；
- 只对可重试错误重试；
- 调用者、任务、耗时、状态和估算成本记录；
- 每日预算与熔断；
- 故障时清晰降级，不伪装成已完成。

公共聊天可继续匿名使用，但必须接受跨实例限流的现实；生产限流应迁移到 Upstash Redis 或同类托管存储。

### 6.7 内容管道

Hermes/飞书只负责选题、生产、审批和发布状态；角色知识真源仍在内容资产库。

生产环境不得依赖本机 CLI、工作目录写入或本地凭证。耗时内容任务逐步改为：

```text
创建任务 -> 返回 jobId -> 后台执行 -> 轮询状态 -> 人工审批 -> 发布
```

## 7. 数据模型调整建议

### 7.1 必须优先修正

1. 所有业务状态统一为常量/enum 和状态转换函数。
2. `Payment` 增加 provider、eventId、transactionId 唯一性和原始事件摘要。
3. 增加独立 `Entitlement`，不要只靠订单 `remark` 解析权益。
4. 增加 `BusinessActivity` 或统一事件表，串起申请、商机、订单、项目和知识回流。
5. 资源领取增加 `(userId, resourceId)` 唯一约束。
6. 知识单元增加来源类型、来源 ID、角色、场景、证据和发布状态。
7. 用户联系方式、项目地址等敏感字段补数据最小化和保留期限。

### 7.2 推荐的核心实体关系

```text
User
  ├── ServiceRequest
  │     └── Opportunity
  │           ├── Proposal (versioned)
  │           ├── Agreement
  │           └── Project
  │                 └── ProjectDeliverable
  ├── Order
  │     └── Payment
  │           └── Entitlement
  └── Consent

Project / ServiceRequest
  -> CaseDraft
       -> KnowledgeUnit
            -> ContentAssembly
```

### 7.3 迁移纪律

`prisma/migrations/` 是生产结构唯一真源。

执行顺序：

1. 生产数据库备份；
2. 只读对账 `schema.prisma`、migration 和生产真实结构；
3. 生成 baseline/reconciliation migration；
4. staging 从空库重建；
5. 做关键数据条数和索引校验；
6. 生产执行 `prisma migrate deploy`；
7. 记录回滚和恢复步骤。

## 8. 30 天实施路线

### 第 1 周：止血与统一真相

**任务**

- 下线或修复缺失收款码的付款入口；
- 移除 Prisma 生产静默写失败；
- 修复订单页 session 空值异常；
- 占位 Webhook 改为明确未启用响应；
- 下线 OPC 旧价格、收入和退款承诺；
- 建立产品、价格、权益、退款的唯一配置源；
- 增加隐私说明和材料提交提示。

**验收**

- 用户不能进入一个看似可付款、实际无法付款的页面；
- 数据库故障不会返回 `ok: true`；
- 全站只能找到一套当前价格和承诺；
- 未登录访问订单页稳定跳转登录。

### 第 2 周：交易和服务主链

**任务**

- 完成人工付款确认和权益幂等；
- 增加订单/支付/权益明确状态；
- 修复优惠券实际计算；
- 服务申请状态机统一；
- “保存到知识库”真实创建来源关联记录；
- 加入请求 ID、标准错误和审计字段。

**验收**

```text
申请 -> 审核 -> 订单 -> 付款通知 -> 后台确认 -> 权益 -> 完成
```

完整走通一次，重复点击、重复确认、数据库中途失败都不会重复发放或制造假成功。

### 第 3 周：前台收敛与真实证据

**任务**

- 主导航收敛为“公开实践 / 免费工具 / 项目合作 / 星火者”；
- 三类角色入口各保留一条主路径；
- 工具结果页只保留一个主 CTA；
- 服务页补输入、输出、周期、验收和不适合人群；
- 发布 3 个真实或脱敏案例；
- 所有重要内容增加角色、场景、动作、证据元数据。

**验收**

- 新用户 10 秒内能判断自己该点哪里；
- 从文章/工具到申请不超过 3 次关键点击；
- 每个服务不再依赖抽象能力词解释价值；
- 至少 3 个案例能展示输入、判断、交付物和结果。

### 第 4 周：行动后台与观测

**任务**

- 后台首页改为今日待办、超时承诺、待付款、待验收、待回流；
- 增加首次响应时间、申请到成交、付款到权益、交付按期率；
- 接入跨实例限流；
- 增加关键 API 集成测试和主流程 E2E；
- 中文字体本地化、关键图片优化、恢复生产 lint 门禁；
- 建立错误告警、备份和恢复记录。

**验收**

- 登录后台后能直接得到今日行动顺序；
- 关键故障能通过 requestId 定位；
- 主链路自动化回归通过；

## 10. 衡量标准：用业务事实替代功能数量

未来每周只看以下指标：

| 指标 | 定义 | 目标方向 |
| --- | --- | --- |
| 首次响应时间 | 服务申请到首次人工回应 | 下降 |
| 工具完成率 | 开始工具到得到结果 | 上升 |
| 结果到申请率 | 工具结果后提交申请的比例 | 上升 |
| 申请到成交率 | 有效申请到确认订单 | 上升 |
| 付款确认时长 | 用户通知付款到后台确认 | 下降 |
| 权益兑现成功率 | 已确认付款中成功开通比例 | 接近 100% |
| 按期交付率 | 到期交付物按时验收比例 | 上升 |
| 知识回流率 | 完成交付中形成案例/知识的比例 | 上升 |
| 复用次数 | 知识单元被内容、工具或服务调用次数 | 上升 |

页面数、组件数、Git 提交数和内容文件数只能作为系统健康指标，不能作为业务进展指标。

## 11. 最终架构判断

### 前端

前端要从“展示我有什么”升级为“帮助用户完成当前决定”。核心是入口收敛、证据具体、边界透明、下一步单一。

### 后台

后台要从“数字资产控制室”升级为“今日行动和承诺履约台”。核心是待办、SLA、状态、责任人、验收和回流。

### 后端

后端要从“尽量不报错”升级为“事实可靠、失败可见、重复可安全重试”。核心是事务、幂等、状态机、权限和审计。

### IP

IP 的增长不靠继续堆页面，而靠每一次真实交付留下：

```text
一个具体问题
一个有边界的判断
一份可使用的交付物
一个可验证的结果
一条可复用的角色知识
```

这才是赞诺网站、内容资产库、星火者社群和 OPC 一人公司能够长期连接起来的技术与商业基础。
